# nooq Document Model & Transaction Protocol

**Status: Draft 1.7 — pre-implementation.** This spec converts
[`PHILOSOPHY.md`](PHILOSOPHY.md) into semantics. It is expected to be
revised by contact with reality, in public, under governance. Sections are
citable by number ("DM-3 forbids that").

**Lineage.** Canonical-bytes and identity rules are adapted from the gooi
project's `protocol/identity.md` (RFC 8785 canonical JSON, SHA-256
fingerprints with exact digest inputs, evidence re-verified at boundaries)
— same author, lineage stated. The proposal/settlement pattern adapts
gooi's `FileProposal` model. What gooi deliberately does not have — CRDT
merge semantics, inline sequence content, and merge-aware revalidation —
is specified here for the first time.

Normative language: MUST, SHOULD, MAY as usual.

---

## DM-1. Layers

1. **Identity & canonical bytes** (DM-2) — how anything is hashed.
2. **Document state** (DM-3) — blocks, tree, inline content.
3. **Operations & transactions** (DM-4) — the one protocol every actor
   uses (PHILOSOPHY §1).
4. **Provenance** (DM-5) — attribution stored in the document.
5. **Suggestions & revalidation** (DM-6) — AI edits as proposals.
6. **Migrations** (DM-7) — CRDT-aware schema evolution.
7. **Sync** (DM-8) — peers, snapshots, digests.
8. **Signed transactions** (DM-12) — envelopes binding transactions to
   actors and their exact effects.
9. **Access rules** (DM-13) — shared, pure, enforced identically by
   every peer.

## DM-2. Identity and canonical bytes

Adopted from gooi `protocol/identity.md`:

- Canonical JSON is [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785).
  Implementations MUST reject duplicate object names, invalid UTF-8, lone
  UTF-16 surrogates, and non-finite numbers. Numbers are IEEE 754 binary64;
  exact integers or decimals beyond that MUST be carried as strings.
  Unicode normalization MUST NOT be applied. Array order is preserved.
- A **fingerprint** is `sha256:` + 64 lowercase hex digits over the UTF-8
  canonical bytes of a structure's *digest input*, defined below. No BOM,
  trailing newline, or whitespace.
- A **block ID** is a 128-bit UUIDv7, hex-encoded, generated by the
  creating actor. Collisions are probabilistically impossible and treated
  as malformed input.
- An **actor ID** is a stable unique string for each actor (human, AI
  session, importer, migration runner). Actor IDs never imply identity of
  persons; they are correlation handles. When a document has access
  rules (DM-13), an actor's Ed25519 public key binds to its actorId
  through the document's `access` header — the ID remains a correlation
  handle; the key is the identity.
- A **Lamport clock** per actor, incremented on each transaction, paired
  with the actor ID for total ordering: `(lamport, actorId)` compared
  lexicographically. Causality between transactions additionally uses a
  version vector per document.

## DM-3. Document state

A document is a forest of **blocks** plus a header:

```json
{
  "docId": "…",
  "schemaVersion": 1,
  "roots": ["<blockId>", "…"],
  "blocks": { "<blockId>": { "…block…": "…" } }
}
```

A **block** is:

```json
{
  "id": "<blockId>",
  "type": "nooq.paragraph/v1",
  "fields": { "…type-defined JSON…": "…" },
  "text": { "…inline sequence CRDT state…": "…" },
  "children": ["<blockId>", "…"],
  "attribution": { "…DM-5…": "…" }
}
```

Rules:

- **DM-3.1** Each block ID appears in at most one `children` array or
  `roots`. The tree invariant. Enforcement under concurrency: DM-4.4.
- **DM-3.2** `fields` is a map of **last-writer-wins registers**, one per
  key. Writes replace values wholesale; there is no deep merge of nested
  JSON. Mergeable structure SHOULD be modeled as child blocks or inline
  content instead. (Boring core: surprising merge semantics are worse
  than none.)
- **DM-3.3** Inline content is a **sequence CRDT** (RGA-class) of
  characters. Formatting attaches to characters as per-character marks,
  never to numeric ranges — concurrent edits cannot strand a mark.
- **DM-3.4** Deletion is a **tombstone**: the block is removed from its
  parent's `children` but its map entry, fields, and inline state persist.
  A tombstoned block remains addressable (PHILOSOPHY §4) and recoverable;
  garbage collection is a non-goal for v1.
- **DM-3.5** Positions are always derived (render-time), never stored as
  truth (PHILOSOPHY §4).

## DM-4. Operations and transactions

The **transaction** is the unit of change and the only entry point to the
document — for humans, AI, importers, and migrations alike (PHILOSOPHY
§1). Durable intent precedes state change (gooi lineage): a transaction is
persisted in the document's append-only **intent log** before it is
applied.

```json
{
  "id": "<uuid>",
  "actor": "<actorDescriptor>",
  "adoptedBy": "<actorId>",
  "lamport": 42,
  "causality": { "<actorId>": 41 },
  "intent": "rewrite-intro",
  "ops": [ "…op objects…" ]
}
```

`adoptedBy` appears only on suggestion-adoption transactions (DM-6.3):
the transaction's `actor` is the proposing actor whose ops are applied
verbatim, and `adoptedBy` names the actor who accepted them.

Operations (all reference block IDs, never positions):

- **DM-4.1 Insert** — `{op:"insert", block:{…full block…}, parent, index?}`
- **DM-4.2 SetField** — `{op:"setField", block, key, value}` (LWW register
  write; carries `(lamport, actorId)` implicitly from the transaction).
- **DM-4.3 TextEdit** — `{op:"textEdit", block, changes}` where `changes`
  is a list of splice steps applied left to right against the block's
  sequence CRDT (DM-3.3):
  - `{retain: n}` — advance n characters without changing them
  - `{retain: n, setMarks: [names] | null}` — also set (or, with null,
    clear) the marks on those n characters
  - `{insert: s, marks?: [names]}` — insert `s` at the current position,
    carrying the given marks
  - `{delete: n}` — delete the next n characters
  Trailing retains MAY be omitted; an empty `changes` list is a no-op.
  Keystroke cost is proportional to the edit, not the block or document;
  and because edits are positioned splices, "the selection covers the
  same characters" is well-defined under remote edits (EB-7).
  *(Draft 1.5: the interim whole-block replacement form is retired; this
  is the shape DM-4.3 always described. Doc changed before code, per
  DM-11.)*
- **DM-4.4 Move** — `{op:"move", block, newParent, newIndex}`. Applied as
  removal from the current parent and insertion at the target within the
  same transaction.
- **DM-4.5 Delete** — `{op:"delete", block}` (tombstone; DM-3.4).
- **DM-4.6 Restore** — `{op:"restore", block, parent, index?}` — reverse
  tombstone. Restore obeys DM-4.4's rule: the new parent MUST NOT lie in
  the restored block's subtree, which may contain tombstoned descendants
  and therefore needs checking even though the block itself is unreachable.
  Descendants that were reparented while a block was tombstoned remain
  where they were placed (placement-register semantics, DM-4.7): reviving
  a block never steals its former children back, and the sequential
  engine realizes this by removing a block from every children list
  before attaching it.
  *(Draft 1.3: subtree rule and reparenting semantics clarified after the
  first op-storm runs produced placement cycles and revived-parent
  collisions through restored blocks; doc changed before code, per
  DM-11.)*

**Concurrent-move resolution (DM-4.7).** Placement authority is a
deterministic LWW **placement register** (block ID → parent or tombstone).
If, after merging, a block's placement was written concurrently by several
peers, the register keeps exactly one winner; every `children`/`roots`
entry that disagrees with the register is ignored by projection (and
physically removed by normalization). The register's resolution MUST be a
pure function of the merged operation set, so every peer computes the
identical forest without communication. The reference Yjs adapter realizes
this with Yjs's native register conflict resolution ((clock, clientID));
adapters whose CRDT exposes lamport clocks SHOULD resolve by greater
`(lamport, actorId)`. *(Draft 1.3 amendment: Draft 1.2 specified
(lamport, actorId) resolution for all adapters, which is unimplementable
above a CRDT that does not expose losing concurrent register values —
Yjs keeps one deterministic winner and discards the rest. Found while
implementing the adapter; doc changed before code, per DM-11.)*

**Edit-vs-delete (DM-4.8).** Order removal and field/text writes are
independent: a concurrently edited-and-deleted block stays removed, keeps
every edit in its tombstone, and is restorable with DM-4.6. UI SHOULD
surface "deleted with later edits."

## DM-5. Provenance

Attribution is part of document state (PHILOSOPHY §5), not merely the log.

- An **actor descriptor** travels with each transaction:
  `{actorId, kind: "human"|"ai"|"importer"|"migration"|"system",
  model?, plugin?}`.
- Each block's `attribution` maintains, per field key and for `text`:
  the last writing `(actorId, lamport)`, plus the creating actor.
- The intent log retains every transaction, including rejected
  suggestions' proposals (DM-6), for the document's life.
- **Adoption provenance:** when a suggestion is accepted, the applied
  transaction records BOTH the proposing actor and the adopting actor
  (`adoptedBy`). AI text in a human's document is never unattributed.

## DM-6. Suggestions and revalidation

An AI edit is a **proposal artifact** — content-addressed, exact, and
evidence-carrying (gooi `FileProposal` lineage) — stored as an ordinary
block of type `nooq.suggestion/v1`. Because it is an ordinary block, it
replicates, syncs, and is addressable like any other content.

The proposal payload:

```json
{
  "base": { "rootDigest": "sha256:…" },
  "ops": [ "…exact DM-4 ops, canonical JSON…" ],
  "evidence": [ {"block": "<blockId>", "contentDigest": "sha256:…", "structureDigest": "sha256:…"} ],
  "context": { "…model, prompt ref, plugin…": "…" },
  "actor": "<actorId>"
}
```

- **DM-6.1 Digests.** Three digests per block:
  - The **content digest** — fingerprint over exactly
    `{type, fields, textDigest}`, where `textDigest` is the fingerprint of
    the canonical rendered `{s, marks}`.
  - The **structure digest** — fingerprint over exactly
    `{children: [{id, structureDigest}]}` — the *content-free* recursive
    shape of the subtree. Because it never incorporates any content
    digest, content drift in a descendant does not change an ancestor's
    structure digest. This is what makes `stale` distinguishable from
    `conflicted` in DM-6.2.
  - The **block digest** — fingerprint over exactly
    `{contentDigest, structureDigest, children: [<child block digests>]}`
    — the full Merkle digest: any change anywhere in a subtree changes
    every ancestor's block digest. The **root digest** is the fingerprint
    over the ordered live `roots` block digests, and thus pins the entire
    document.
  Evidence records the content and structure digests. Digests are defined
  over the **alive forest** — blocks reachable from `roots` — which is a
  single-parent spanning forest by construction and therefore acyclic:
  every alive block has exactly one digest, computed along its unique
  path from a root. Unreachable blocks (tombstoned, or orphaned by
  placement cycles from concurrent merges) have no digests; revalidation
  reports them as `tombstoned` or `missing` before any digest comparison,
  so revalidation never crashes on states concurrent editing legitimately
  produces.
  *(Draft 1.2 amendment: Draft 1.1 defined the structure digest over
  child block digests, which include content — so any descendant content
  edit flipped every ancestor's structure digest and `stale` vs
  `conflicted` collapsed again. Found by the first `evaluate()` test run;
  doc changed before code, per DM-11.)*
- **DM-6.2 States.** `fresh → accepted | rejected | stale | conflicted`.
  States are NOT stored as truth; they are **derived** by
  `evaluate(proposal, state)` — a pure function, so all peers agree
  without communication:
  - every evidence digest matches → `fresh`
  - content drift in an evidence block (text/fields) → `stale`
  - structural drift (target tombstoned, moved out from under a
    structural op, or tree no longer matches `base`) → `conflicted`
- **DM-6.3 Accept** is an ordinary transaction applying the proposal's
  `ops` verbatim, with adoption provenance (DM-5). The accepting
  transaction is authored by the **proposing** actor (block-level
  attribution keeps pointing at the AI: its text is never unattributed)
  and carries `adoptedBy` naming the accepting actor. Acceptance also
  writes a `status` field (`"accepted"`) to the suggestion block and
  tombstones it in the same transaction, so the verdict is derivable
  from document state, not only from the log. Implementations MUST
  apply the ops as written — acceptance is an explicit human act against
  a displayed diff, not a re-derivation — so a forced accept of a stale
  proposal can fail outright (e.g. an index no longer fits); failing
  loudly is correct. If `evaluate` is not `fresh`, the UI MUST present
  the stale/conflicted evidence; applying anyway is permitted (the
  writer decides) and recorded.
- **DM-6.4 Reject** tombstones the suggestion block after writing
  `status: "rejected"` to it in the same transaction; the proposal
  payload persists in the tombstone and in history.
  *(Draft 1.4: `adoptedBy` formalized on the transaction sketch; the
  author-of-record rule and the status-field verdict added while
  implementing the suggestion lifecycle; doc changed before code, per
  DM-11.)*
- **DM-6.5 Revalidation is continuous:** status is recomputed on every
  state change, so a suggestion visibly goes stale the moment a concurrent
  edit invalidates its evidence. This is the property gooi enforces by
  *failing* adoption; in nooq, drift is life, so the proposal *degrades
  visibly* instead of aborting silently.
- **DM-6.6** Suggestions-on-suggestions are a v1 non-goal; a suggestion
  whose evidence includes another suggestion block simply treats it as
  content.

## DM-7. Migrations

- `schemaVersion` exists at document level and per block `type` version.
- A migration is a **pure, idempotent, order-independent** function over
  block state, shipped in the plugin that owns the block type. Because
  pure and order-independent, concurrent application on different peers
  converges — CRDT-aware by construction (PHILOSOPHY §8).
- Migrations MUST be monotone (old → new only) and MUST NOT remove or
  rewrite attribution.
- Applied lazily on read and explicitly on write; never a background
  mutation of live content.

## DM-8. Sync and snapshots

- Peers exchange transactions (or state vectors + deltas). Any conformant
  transport works. The wire envelope, handshake, bootstrap verification,
  and the server-as-peer contract are specified in [`SYNC.md`](SYNC.md)
  (SW-1..SW-11). A server, including a hosted nooq service, is a peer
  with no special authority (PHILOSOPHY §2).
- A **snapshot** is a full-history delta plus its claimed root digest
  (SW-3/SW-5); the **root digest** supports O(1) staleness checks between
  peers and local verification of bootstrap data.
- Presence, cursors, and selection are ephemeral **awareness**, never
  document state; cursors anchor to block identity (SW-7, per DM-4).

## DM-9. Reference implementation mapping (informative)

- State: Yjs document — `blocks` as `Y.Map` of `Y.Map`; `children` as
  `Y.Array` of ids; inline as `Y.Text` with per-character attributes;
  LWW fields wrapped as `{value, lamport, actorId}` registers
  (application-level, DM-3.2). ProseMirror state is a **projection**
  maintained by a binding layer; it is never the authority. All changes
  — typing included — enter through nooq transactions (PHILOSOPHY §1).
  Yjs, Automerge, ProseMirror: all MIT, satisfying the Covenant.
- The DM-4.7 resolution is implementable above either library's primitives
  as a merge-normalization pass; if a library's native semantics already
  guarantee it, the pass is a no-op assertion.

## DM-10. Open problems (tracked honestly)

1. **Move under concurrent moves to the same parent** — DM-4.7 resolves
   deterministically, but the UX of "lost" moves needs study.
2. **Mark churn** under heavy concurrent formatting; per-character marks
   may bloat; may need mark-run compaction (does not change semantics).
3. **Very large documents** — snapshot compaction and lazily materialized
   subtrees; v1 assumes whole-document residency.
4. **Evidence granularity** — block digests pin whole blocks; finer
   (per-run) evidence would reduce false staleness.
5. **Suggestion UX for structural conflicts** — the data model distinguishes
   `stale` from `conflicted`; whether writers care is an open question.
6. **Grant revocation and key rotation** — grants are append-only in v1
   (DM-13); removing an actor means forking to a new secured document.
7. **Bounded holds** — an envelope held for an ungranted signer or an
   unresolved base (DM-12) may wait indefinitely; peers need an eviction
   policy that does not change any verdict.

Same rule as PHILOSOPHY: citable by section in review and design debates.
A PR that violates DM-x is wrong, or DM-x is — in which case the spec

## DM-12. Signed transactions

A nooq transaction produces exactly one Yjs transaction and one
incremental update. A **signed envelope** binds the transaction to its
actor and its exact effects:

```json
{
  "tx": { "…the nooq transaction…": "…" },
  "client": "<yjs clientID>",
  "clocks": { "from": 0, "to": 9 },
  "updateDigest": "sha256:…",
  "sig": "<base64 Ed25519 signature>"
}
```

- The signature is Ed25519 over the canonical JSON (DM-2) of
  `{docId, tx, client, clocks, updateDigest}`.
- The update may contain only structs from the declared client (a Yjs
  clientID bound to the actor for this envelope), in the declared
  contiguous clock range. `updateDigest` is the SHA-256 fingerprint of
  the update bytes: an update that does not match its envelope is
  tampered and MUST be dropped.
- Its delete set may target only blocks the access rules (DM-13) allow.
  Deletes are resolved against every retained item they cover, not only
  items whose first clock they name.
- **Signer binding.** An envelope's signer MUST be the transaction's
  author: `tx.adoptedBy` for an adoption, otherwise `tx.actor.actorId`.
  In an adoption, `tx.actor` MUST be the proposing actor recorded in the
  settled suggestion block. A transaction that names `adoptedBy` without
  settling a suggestion is malformed.
- **One log entry.** The update's only write to the intent log is exactly
  one entry, canonically equal to `tx`. No envelope deletes or rewrites a
  log entry, and no envelope writes outside the document's own roots
  (`blocks`, `roots`, `placement`, `access`, `log`). Bookkeeping is
  document state: provenance (DM-5) is only as strong as the log.
- **Causal readiness.** A struct or delete the receiver cannot resolve
  against the update itself or its local store has an unknown target.
  Such an envelope is **held**, exactly like an ungranted signer, and
  re-evaluated as admissions arrive. It is never authorized on a partial
  view, so every peer reaches the same verdict.

*(Draft 1.7 amendment, proposals/0001 comment period: Draft 1.6 left the
log, unknown roots, mid-item deletes and unresolved parents outside
classification, and bound neither signer nor kind to the transaction. A
probe showed a suggester could delete `access` (reverting to open mode)
or forge log entries, and a writer could sign as another actor. Doc
changed before code, per DM-11.)*

## DM-13. Access rules

The document header gains an optional `access` value:

```json
{
  "owner": { "actorId": "…", "key": "<base64 Ed25519 public key>", "kind": "human" },
  "grants": [ { "actorId": "…", "key": "<base64>", "kind": "human", "role": "writer" } ],
  "nonce": "…"
}
```

- **Secured at genesis.** A document is secured or open from its first
  byte, decided by its ID alone: a secured document's ID is
  `nooq:` + the fingerprint (DM-2) of `{owner, nonce}`. Its first access
  write is the genesis envelope, signed by that owner. Until a peer has
  admitted genesis, every other envelope is held. An open document (any
  other ID) never gains `access`; securing it means forking to a new
  secured document. Absence of `access` therefore never turns a secured
  document open, and no arrival order decides who owns a document.
- `access` is written only by owner-signed envelopes (DM-12). The owner
  and nonce never change, and each write's grants MUST extend the
  current grants unchanged (append-only in v1; revocation means forking,
  DM-10.6). Deleting or rewriting `access` any other way is an access
  write and is denied.
- **Kinds are granted.** Each grant (and the owner) binds a `kind`. An
  envelope's `tx.actor.kind` MUST equal its signer's granted kind; in an
  adoption, the proposer's kind MUST equal the proposer's grant when one
  exists. An AI cannot write as a human by relabeling itself.
- Roles:
  - **writer** — any op.
  - **suggester** — may create and attach `nooq.suggestion/v1` blocks
    only. Actors of kind `ai` default to suggester (PHILOSOPHY §5).
  - **reader** — no ops.
- Accept and reject require a writer. An adoption is signed by its
  `adoptedBy` actor, and its ops MUST canonically equal the proposal's
  ops (DM-6.3's "verbatim" now verified, not promised).
- `authorize(access, envelope, touched)` is a **pure function**. Every
  peer — relays included — applies it identically before applying an
  update; no peer applies any other content policy (SW-1.2).
- An envelope whose signer is validly signed but not yet granted is
  **held pending** and re-evaluated when grants arrive. An envelope that
  fails verification or authorization is never applied or relayed.
- An open document behaves exactly as before: single-player or
  trusted-peers mode, with no rules but the CRDT's.

*(Draft 1.6, per proposals/0001. Draft 1.7: secured-at-genesis IDs, kind
binding, append-only enforcement and access deletes, per the same
comment period.)*
